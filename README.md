# HTTP Download Benchmark

Небольшой CLI-инструмент для замера последовательной загрузки по HTTP(S). Делает
заданное число GET-запросов, читает тело потоком и считает время, объём, фазы
соединения и скорость. Использует только стандартную библиотеку Python и не
сохраняет файл на диск.

## Что умеет

- Выполняет N запросов по одному, без параллельности.
- Читает ответ чанками по 64 КиБ, поэтому не зависит от размера файла.
- Разбивает время запроса на фазы: DNS, TCP, TLS handshake, TTFB, чтение тела.
- Считает среднее, медиану, стандартное отклонение, min/max, p90/p95.
- Считает два вида скорости: по телу (байты / окно передачи тела) и агрегированную
  по запросу (байты / полное время, включая соединение).
- `--warmup` прогревает кэши и соединения до измерения, `--keep-alive`
  переиспользует соединение, `--cache-bust` обходит кэш, `--delay` задаёт паузу.
- Один общий таймаут-бюджет на запрос: соединение, заголовки, тело и все
  редиректы вместе укладываются в `--timeout`.
- Следует редиректам (до 10) и обрабатывает таймауты, не-2xx ответы и обрывы.
- Прогресс пишется в stderr, отчёт — в stdout; есть `--json` и `--csv` для CI.
- По Ctrl+C печатает частичную сводку и выходит с кодом 130.

## Запуск

```bash
python main.py --help
```

Или после установки пакета:

```bash
pip install .
httpbench "https://speed.cloudflare.com/__down?bytes=10000000" -n 5
```

Пять запросов с таймаутом 120 секунд:

```bash
python main.py "https://speed.cloudflare.com/__down?bytes=10000000" -n 5 --timeout 120
```

На Windows вместо `python` можно использовать `py`.

### Аргументы

| Аргумент | Описание |
|---|---|
| `url` | Обязательный URL со схемой `http://` или `https://`. |
| `-n`, `--requests COUNT` | Число запросов, целое от 1. По умолчанию 10. |
| `-t`, `--timeout SECONDS` | Общий таймаут-бюджет одного запроса (включая редиректы). По умолчанию 30. DNS-lookup прервать нельзя, поэтому реальное время может его немного превысить. |
| `--warmup COUNT` | Запросы до измерения, в статистику не попадают. По умолчанию 0. |
| `--keep-alive` | Переиспользовать соединение между запросами вместо нового на каждый. |
| `--delay SECONDS` | Пауза между измеряемыми запросами. По умолчанию 0. |
| `--cache-bust` | Уникальный параметр `_=...` в URL каждого запроса против кэша. |
| `--json` | Отчёт в JSON на stdout. Нельзя вместе с `--csv`. |
| `--csv` | По строке CSV на запрос на stdout. Нельзя вместе с `--json`. |

## Две скорости, а не одна

- **Body transfer speed** — байты, делённые на окно между первым и последним
  байтом тела. Это «чистая» скорость передачи данных: без DNS, TCP, TLS и
  ожидания заголовков.
- **Aggregate request speed** — байты, делённые на полное время запроса.
  Включает соединение и заголовки; на маленьких файлах заметно ниже.

## Единицы

Объём считается в десятичных мегабайтах: `1 МБ = 1 000 000 байт`. Это не мебибайты.
Скорость в Мбит/с использует десятичные мегабиты: `1 Мбит/с = 1 000 000 бит/с`.
В одном байте 8 бит, поэтому `1 МБ/с = 8 Мбит/с`. Время выводится в миллисекундах.

## Статистики

По успешным запросам считаются: среднее, медиана, стандартное отклонение
(выборочное, n−1), min/max, p90 и p95 (линейная интерполяция, как в NumPy
по умолчанию). Для фаз считается среднее по тем запросам, где фаза реально
выполнялась: на переиспользованном соединении DNS/TCP/TLS пропускаются и не
разбавляют среднее нулями.

## Ошибки

Если запрос завершился ошибкой, скрипт пишет её в строке запроса, продолжает
серию и возвращает код 1 после завершения. В статистику попадают только
успешные запросы. Причины группируются по одинаковому тексту.

Реальный прогон против `speed.cloudflare.com` из сети с ограниченной полосой
(3 из 5 запросов упёрлись в общий 30-секундный дедлайн уже во время тела,
что видно по полученным байтам; суммарно запрос не превысил бюджет):

```text
[warmup 1/1]                 200      1,121.99        10,000,000  OK
[1/5]        200     30,104.49            21,882  ERROR: timeout after 30 s
[2/5]        200     30,094.98            21,732  ERROR: timeout after 30 s
[3/5]        200     30,104.14            21,732  ERROR: timeout after 30 s
[4/5]        200      1,049.62        10,000,000  OK
[5/5]        200      1,067.22        10,000,000  OK

...

Failure reasons:
   3x  timeout after 30 s
```

| Код | Значение |
|---|---|
| 0 | Все запросы успешны. |
| 1 | Есть ошибки или ни один запрос не завершился успешно. |
| 2 | Неверные аргументы командной строки. |
| 130 | Запуск прерван с клавиатуры; печатается частичная сводка по завершённым запросам. |

Редиректы выполняются автоматически, до 10 переходов, и все вместе делят
один таймаут-бюджет с исходным запросом. Если сервер передал `Content-Length`,
скрипт проверяет, что тело получено полностью. Для chunked ответов завершение
проверяет `http.client`. Тело без `Content-Length` и без chunked читается до
закрытия соединения.

Если получилось `0 / N`, смотрите блок `Failure reasons`:

| Сообщение | Что проверить |
|---|---|
| `DNS error` | Домен, DNS и доступность сети. |
| `TLS error: CERTIFICATE_VERIFY_FAILED` | Корневые сертификаты, прокси, TLS. |
| `HTTP 403/404/429` | Доступ, путь к файлу, лимиты сервера. |
| `timeout after N s` | Увеличить `--timeout` или проверить канал. |
| `connection error` | Порт, файрвол, жив ли сервер. |

## Таймаут

По умолчанию на один запрос даётся 30 секунд **суммарно**: DNS, TCP, TLS,
заголовки, тело и все редиректы вместе. Перед каждой сокетной операцией
сокету ставится оставшийся бюджет, поэтому дедлайн невозможно «перезапустить»
новым редиректом или медленным телом. Единственное исключение — сам DNS-lookup
(`getaddrinfo` блокирует поток целиком и не прерывается), после него бюджет
проверяется и обрывается, но превышение равно длительности lookup.

## Ограничения

- Запросы выполняются по одному, это не проверка максимальной пропускной
  способности канала.
- Без `--keep-alive` каждый запрос открывает новое соединение; DNS, TCP и TLS
  входят в измеренное время. На маленьких файлах накладные расходы доминируют.
- С `--keep-alive` пул один: если сервер закрыл соединение на своей стороне,
  клиент повторяет запрос один раз на свежем соединении (это видно по счётчику
  фаз). Прерванный после отправки запроса ответ не восстанавливается.
- Кэш CDN может искажать результат; `--cache-bust` помогает, но убивает кэш
  на стороне origin — прогрев (`--warmup 1`) работает только при включённом кэше.
- `getaddrinfo` не прерывается: DNS-lookup может превысить дедлайн на свою
  длительность.
- Wi-Fi, VPN, прокси, загрузка CPU и TLS-шифрование влияют на замер.
- Тело не сохраняется, поэтому проверить целостность файла после загрузки
  нельзя.
- Если нет `Content-Length` и сервер закрывает соединение вместо chunked,
  ранний обрыв не всегда можно отличить от нормального конца.
- Скрипт шлёт `Accept-Encoding: identity`, но если сервер всё равно вернул
  `Content-Encoding`, считаются полученные байты без распаковки.
- `urllib`-прокси из переменных окружения `HTTP_PROXY`/`HTTPS_PROXY` здесь
  не используются: клиент ходит напрямую.

## Структура

```
httpbench/
  network.py   — клиент на socket/ssl/http.client: фазы, дедлайн, keep-alive
  stats.py     — агрегаты: медиана, p90/p95, std dev, скорости, средние фаз
  report.py    — текстовая сводка, JSON и CSV; все функции принимают поток
  cli.py       — argparse, цикл бенчмарка, коды возврата
main.py        — совместимая точка входа `python main.py`
tests/         — unittest + локальный HTTP/HTTPS-сервер
```

## Тесты

```bash
python -m unittest discover -s tests -v
```

Тесты не требуют внешних пакетов. Поднимается локальный HTTP/HTTPS-сервер
(self-signed сертификат генерируется один раз и лежит в `tests/certs/`) и
проверяются: успешный ответ с фазами, редиректы (включая цепочку длиннее
лимита и редирект на не-http схему), 404, chunked, обрезанный и мусорный
`Content-Length`, drip-feed тело по 1 байту (дедлайн срабатывает именно
в цикле, а не на блокирующем чтении), stalled headers/body, тело до EOF,
отказ соединения, ошибка DNS, самоподписанный HTTPS, retry на «протухшем»
keep-alive, частичная сводка по Ctrl+C, JSON/CSV, коды возврата через
запуск `main.py` отдельным процессом и разбор аргументов.

Часть тестов использует тайминги (0.15–0.6 с) с запасом; на сильно
загруженном CI они могут флакнуть.

CI (`.github/workflows/tests.yml`): ruff, mypy, покрытие (порог 85%) и тесты
на Ubuntu (Python 3.10/3.12/3.14) и Windows (3.12/3.14).

## Требования

- Python 3.10 или новее.
- Только стандартная библиотека: `http.client`, `socket`, `ssl`, `argparse`,
  `unittest`.
- Внешних пакетов нет; dev-инструменты (ruff, mypy, coverage) нужны только
  для разработки и запускаются в CI.
